# 图片理解模型路由设计

## 1. 背景与目标

SunCode 的主模型可能只接受文本，例如 OpenCode Go 下的 DeepSeek；同一供应商中又可能存在接受图片输入的模型。图片理解路由允许用户继续使用原主模型完成规划、工具调用和代码修改，仅在需要观察图片时委托同一供应商下的视觉模型执行一次性识别。

本功能解决三个问题：

1. 图片是否污染主 Agent 上下文。
2. 如何从模型目录自动判断图片输入能力，并处理目录信息滞后。
3. 如何把图片理解与图片生成、完整子 Agent 隔离开。

第一版只支持“同一供应商、单个视觉模型”。不做跨供应商自动路由，也不做多个模型的隐式故障转移。

## 2. 顶层架构

```text
用户上传图片 / 主 Agent 发现本地图片
  │
  ▼
图片理解服务
  ├─ 解析当前供应商配置
  ├─ 选择主模型或已配置的视觉模型
  ├─ 发起独立的一次性多模态请求
  └─ 只产生精简文字观察结果
  │
  ├─ 纯图片问答 → 直接作为最终答复返回
  └─ 混合任务 → 可信视觉观察 → 主 Agent 继续执行
```

视觉调用不是完整子 Agent：它没有工具、项目记忆、历史消息、任务循环或完整 System Prompt。它只接收图片和当前问题，完成后立即结束。

核心代码：

- `src/worker/models/vision-routing.ts`：能力判定与视觉目标选择。
- `src/worker/models/vision-analysis.ts`：共享的一次性图片理解服务。
- `src/worker/agent/agent.ts`：上传附件预处理、可信观察注入和纯图片问答快速通道。
- `src/worker/tools/inspect-image.ts`：一次性图片理解调用。
- `src/worker/tools/read.ts`：图片文件不再以 Base64 文本返回。
- `src/renderer/components/settings/ModelSelector.vue`：视觉模型与能力覆盖设置。

## 3. 决策一：不会把图片放入主模型上下文

### 3.1 被否决的方案

旧 `read` 工具读取图片后，把完整 Base64 放进字符串工具结果。该字符串随后会进入主 Agent 的 `contextMessages`，存在以下问题：

- Base64 大幅占用主模型上下文窗口。
- 文本模型无法把 Base64 当作视觉输入理解。
- 图片内容会进入会话持久化、诊断和裁剪链路。
- pi-ai 对不支持图片的模型可能忽略真正的图片块，不能依赖下游兜底。

因此禁止把图片二进制或 Base64 作为普通工具文本返回主模型。

### 3.2 当前实现

`read` 遇到 PNG、JPG、JPEG、GIF 或 WEBP 时只返回路径和操作提示：使用 `inspect_image` 并提供一个聚焦问题。图片字节不会进入主上下文。

`inspect_image` 创建一个独立 pi-ai 请求，请求中只有：

- 一条固定、精简的视觉检查 System Prompt。
- 当前 `question`。
- 一个标准 `{ type: 'image', data, mimeType }` 图片块。
- 空工具列表。

请求结束后，主 Agent 只收到以下文字：

```text
视觉模型：provider/model
图片：absolute/path.png
问题：需要检查的目标

视觉模型返回的观察结果
```

视觉结果限制为最多 12,000 字符，视觉模型输出上限为 2,048 tokens。因此主上下文消耗来自“观察结果文字”，不来自图片本身。

上传附件由 Worker 直接传给同一个图片理解服务，不要求主 Agent 先把附件保存为本地文件。对于需要主 Agent 继续工作的混合任务，原始图片块会被替换成：

```xml
<vision_observation provider="provider" model="model">
有界的可见信息
</vision_observation>
```

System Prompt 把该标签定义为已经从用户附件产生的可信视觉证据，并明确禁止主模型仅为找回同一附件而搜索会话文件、运行事件、日志或 Base64，也禁止无明确复核要求时再次调用 `inspect_image`。这项约束解决了“视觉模型已经识别成功，主模型仍恢复原图并重复识别”的上下文和延迟污染。

### 3.3 上下文与计费边界

| 内容 | 视觉模型请求 | 主模型上下文 |
|------|-------------|-------------|
| 原始图片 | 是 | 否 |
| 当前图片问题 | 是 | 工具调用参数中可见 |
| 完整聊天历史 | 否 | 是 |
| 项目记忆与教训 | 否 | 是 |
| 视觉观察文字 | 输出 | 是 |

视觉模型仍会产生独立的供应商用量，但不会占用主模型的图片输入或把主上下文复制给视觉模型。

### 3.4 纯图片问答快速通道

“这张图片展示什么”“读取截图文字”“描述照片内容”等只需要视觉事实、且没有修改代码、创建文件、执行命令等动作意图的请求，完成视觉调用后直接结束本次运行：

```text
附件 + 用户问题 → 视觉模型 → 最终答复
```

该路径不加载项目技能、AGENTS.md、记忆、教训、完整工具列表，也不启动多轮 AgentLoop。空文字附件默认视为“简洁描述图片”。如果请求包含修改、修复、实现、创建、运行、部署等动作意图，则不会命中快速通道，仍由主 Agent 基于可信视觉观察继续完成任务。

快速通道只省略不必要的主模型二次组织，不会复用主 Agent 的上下文；视觉调用仍然是独立计费的一次性请求。

## 4. 决策二：自动能力识别与手动覆盖

### 4.1 自动识别来源

内置模型通过 `@earendil-works/pi-ai` 的模型目录发现。自动判断规则是：

```ts
Array.isArray(model.input) && model.input.includes('image')
```

主进程的模型发现接口已经把该结果暴露为 `supportsImages`。Renderer 的 `ModelOption` 保留这个字段，用于筛选“图片理解模型”下拉框和展示图片能力标记。

自定义端点模型可以通过 `CustomModelEntry.supportsImages` 声明能力；构造 pi-ai 模型对象时会生成 `input: ['text', 'image']`。

### 4.2 为什么需要手动覆盖

模型目录可能晚于供应商实际上线时间，也可能存在错误标注。设置中为每个供应商保存：

```ts
interface VisionProviderSettings {
  model: string;
  capabilityOverrides: Record<string, boolean>;
}
```

能力判定优先级为：

1. `capabilityOverrides[modelId]`。
2. 模型目录的 `model.input`。
3. 未知时视为不支持。

用户可把每个模型设为“自动识别”“支持图片”或“不支持图片”。手动设置为支持时，视觉请求会复制模型对象，并只对本次请求补充 `input: ['text', 'image']`，确保 pi-ai 不会在协议转换阶段过滤图片。原始模型目录不会被全局篡改。

## 5. 模型选择规则

功能关闭时，`inspect_image` 明确返回设置提示，不尝试图片调用。

功能开启后：

1. 如果当前主模型支持图片，使用当前模型执行隔离的一次性视觉请求。
2. 如果当前主模型不支持图片，读取当前供应商的手动选择。
3. 视觉模型必须能从同一供应商加载，并通过自动能力或手动覆盖判定。
4. 未配置、模型不存在或能力不成立时明确失败，不把图片回退为 Base64 文本。

配置按供应商保存，避免切换主供应商后误用旧供应商的凭据或模型。

## 6. 图片生成与图片理解的边界

图片理解使用普通聊天模型的多模态输入能力，调用 `completeSimple`。

图片生成使用 pi-ai 独立的图片生成模型与 `generateImages` API。两者不共享设置字段，原因是输入输出协议、工具参与方式和计费口径不同。“绘画模型”不能作为图片理解路由的隐式来源。

## 7. 安全与失败策略

- 第一版仅接受本地 PNG、JPG、JPEG、GIF、WEBP。
- 单个图片最大 20 MB。
- 不自动跨供应商发送图片。
- 不自动轮询多个视觉模型。
- 不记录或返回图片 Base64。
- 模型无文字输出、返回错误或加载失败时，工具明确失败。
- API Key 沿用当前供应商的设置；自定义端点使用其自身 Key。

## 8. 当前范围与后续扩展

当前版本完成设置页、能力识别、手动覆盖、本地图片工具、用户上传附件路由、纯图片问答快速通道和 `read` 防 Base64 污染。

Browser/Computer Use 截图等来源后续应统一转换为图片制品并复用同一个视觉调用服务。接入这些来源时必须继续保持同一原则：图片只进入隔离的视觉请求，主 Agent 只接收有界的文字观察结果。
